# Retries for failed emails and webhooks (November 2026)

Branch `claude/retry-emails-webhooks`, based on `origin/main` at 1ca4a50 (after #636). A first-month item from the backend audit.

## What was wrong

- **An email was sent once.**
  - If Resend didn't answer, timed out, said "too many requests" or had a server error, the email was lost.
  - Website status only listed it as failed.
- **A webhook was tried three times within about a second.**
  - A receiver that was down for longer missed the event.
  - Only the last failed body per endpoint was kept, for a manual retry.

## What changed

1. **A retry list** (`OutboxMessage`, migration `20261119180000_outbox_retries`; `lib/outbox.ts`).
   - **What is kept:** a failure that may pass. That is no answer, a timeout, "too many requests" (429) or the other side's server error (5xx).
   - **When it is tried again:** by the hourly job (`app/api/internal/retry-outbox`), which the Worker runs at the top of each hour beside the refund check.
     - The tries come 1, 2, 4, 8 and 8 hours later: six tries over about a day.
     - A failed run of the job alerts the owner, like the other scheduled jobs.
   - **When a try works:** the message is marked sent, and its content removed.
   - **Giving up:** after the sixth failed try, or a refusal, the message is given up and its content removed. The activity log says so ("outbox.gave_up").
   - Finished messages are deleted after two weeks.
2. **Emails** (`lib/email.ts`).
   - Every try of an email carries the same idempotency key, so Resend sends it once even if an earlier try went through after all.
   - A refusal (another 4xx, such as a bad address or an unverified sender domain) is not tried again.
   - A password reset is never kept: its link expires in 30 minutes, and the customer can ask again.
   - Each try is in the email log in Website status, as before.
3. **Webhooks** (`lib/webhooks.ts`).
   - Each event now has an `id`, the same on every try, so a receiver can skip one it already has.
   - After the three quick tries, a delivery still failing is kept for the hourly job.
   - The endpoint still shows the failure and keeps the body for "Retry", as before. A manual retry is not kept again.
   - Each try gets a fresh timestamp and V2 signature.
   - A delivery to an endpoint since removed or turned off is given up.

## Not changed, on purpose

- **Push notifications and Meta events** are not retried yet.
- **No new page:** the email log in Website status and each webhook's status already show failures.
- **`RESEND_API_URL`** lets local checks point at a stand-in for Resend. Production leaves it unset.

## Verification

- `npm run typecheck`, `npm test` (1326 pass) and `npm run backend:audit` pass. `tests/retry-outbox.test.ts` adds 8 tests.
- **The migration** was generated by Prisma. `prisma migrate diff`, the check CI runs, finds the schema and the migrations the same.
- `npm run build:cloudflare` with the CI environment passes.
- **16 checks pass on the production build,** with the local Postgres database. A stand-in for Resend and a webhook receiver failed first, then worked:
  - **Emails:**
    - a sign-up email that got 503 was kept;
    - the hourly job sent it, with the idempotency key of its first try;
    - it is marked sent, with its content removed, and the email log shows it sent;
    - an email refused with 422 was not kept;
    - a password reset that got 503 was tried once and not kept.
  - **Webhooks:**
    - a customer.created webhook that got 500 was tried three times with one event id, then kept;
    - the endpoint showed the failure;
    - the hourly job delivered it, with the same id and a fresh timestamp and V2 signature;
    - the endpoint showed it delivered.
  - **Giving up:** a delivery to a removed endpoint was given up, and the activity log says so.
  - **The job** refuses a request without the key or bearer (401).
- **The local store was left as it was** (restored from the dump).
